02

三个案例：范式长什么样

手册第一章 · 研发范式实践案例

AIDC 数字投手为 Alibaba.com 商家提供一站式广告服务。6 人小队发起专项，愿景是打造一个能自动诊断广告效果、实时优化投放策略、具备丰富代操经验的「数字投手」。

三时期组织演进

  1. 超级个体期——单人指挥 3～5 个会话，一人干 2～3 人的活；但产能锁在个人电脑与单个会话里，难以被团队协作和继承。
  2. 数字员工期——搬上云上智能体运行时，统一结构输出、每周多次交付；但人沦为传令兵和调度员，卡在协作上。
  3. 云上 Scrum——自建人机沟通专线（「数字员工要有自己的钉钉」），按业务域组织协作，完成八成能力交付；不排期、不开日会、不总结会。

经验 / 手脚 / 头脑三分法

不用纯 ReAct——「能推理」不等于「可控」。

  • 经验——专家知识提炼为「问题 / 证据 / 处方 / 适用条件」的结构化结论。
  • 手脚——状态、权限、参数约束由最接近事实的系统预计算，给出可操作清单。
  • 头脑——只在可控空间内推理取舍，决策可解释。
  • 评测——黄金用例、统一评分表、多专家评分，红线一票否决。

两条数据闭环

  • 经验 Loop——策略挖掘与策略生产拆给两个数字员工，经结构化契约交接。
  • 手脚 Loop——线上失败轨迹聚类定因 → 补齐能力 → 回归评测 → 人工发布 → 新轨迹回流。
  • 人的工作收敛为两件事——Loop 维护（环境与验证），与寻找真需求（用增长预估工具评估需求收益）。

千问研发团队用 Agent 重构用户增长体系，打造投放执行、策略、数据分析、预算规划、素材生产的工业化智能运营系统——业务唯一目标是带动用户规模增长，研发目标是用 Agent 重构传统开发流程。

三阶段实践

  1. 粗放探索与能力验证——约 15 名服务端工程师分头探索、每周分享；代码生成速度达数倍至约 10 倍解读版转述口径。
  2. 标准化与存量工程适配——边际收益下降，难题变成「AI 看懂老代码」。
  3. 提升 SDLC 覆盖度——进入需求、方案、拆解、编码、联调、排障、文档全流程，重点转向组织上下文、明确边界、建立验证机制。

四个关键环节

  • 项目理解（Docs / Graph / Rules）——Docs 解决「为什么这样设计、如何寻找」，Graph 精确查询「在哪里、谁调用谁、改动影响什么」，Rules 把团队经验固化为可执行约束。
  • 需求理解前置澄清——不假设需求完整，AI 主动追问隐含决策（如「生成公开分享链接」背后的撤销机制、访问控制、数据一致性），沉淀为可追溯的 Spec 与 Tasks，在成本最低的阶段暴露风险。
  • 可靠编码（TDD 与链路幂等）——TDD 把「代码是否正确」转为可观察、可重复的执行反馈；幂等由请求入口、数据库事务、消息发布消费多环节共同保证；测试聚焦需求边界、关键分支、已知故障模式，不唯覆盖率。
  • 线上排障（TraceId 证据链）——统一 TraceId 打通日志、上下游状态与代码调用关系；先采证据、再推根因；固定证据采集方式、升级条件与结论格式。

研发重心的迁移

从「写高质量代码」迁移到问题定义、上下文组织、边界设计、文档表达和结果验证；协作形态从「多人分工协作一个需求」转向「单个个体对一个需求端到端负责」。下一步：把「个人使用 AI 的能力」转化为「组织稳定交付的能力」。

万有无界是企业级人与 Agent 协作平台。平台型产品支撑多行业多场景，复杂需求横跨身份权限、消息协作、任务资产管理多模块且多端规则需一致——过去在评审、设计、开发、联调的多次交接中，需求背景、约束与验收标准容易遗漏、偏差。

关键做法

  1. 三元任务定义——一个研发任务 = 上下文资产（解决什么问题）+ 工程执行环境（修改发生在哪里）+ 验证证据（证明结果成立），首尾闭环，验证产生的新事实回流沉淀。
  2. 评审前先做可操作原型——产品经理在评审前把业务目标做成基于真实项目代码、可直接操作的交互原型，讨论对象从抽象描述变为真实行为；评审结论回写产品文档，范围与优先级仍由产品负责人判断。
  3. 设计师在真实工程中交付——独立分支 + 工程 Skill，基于真实页面入口、组件树、设计 Token 完成可交互实现，研发直接继承分支；设计协作从单向交接变为双向反馈。
  4. 统一工程工作区 Workspace——先判断目标端、改动类型与共享范围；公共能力变化提升为「跨工程契约」；联调确认「变更在真实环境中成立」，避免在陈旧依赖上误判「已修复」。
  5. auto bug fix 现场采集——插件把版本、环境、页面入口、复现步骤、请求日志、测试数据、受影响范围打包进缺陷上下文；同版本同环境复现 → 修改 → 回到相同页面状态真实验收；分云端即时自动处理与本地周期集中处理两条路径。

03

五大共性挑战

手册第二章 · 实践中的挑战
1

环境与验证驱动难题2.1

沿既有流程做 workflow 化改造只是过渡形态——它优化的是「人如何使用 AI」，而非「AI 如何使用研发环境」；真正的 Agentic 方向是让 Agent 自主获得验证信号并持续推进任务。出路是四项基建：业务领域知识构建、可复现可调用的研发环境、分层验证体系（秒级编译单测 / 分钟级集成契约 / 人工只判业务价值、体验与伦理）、研发系统 AI Friendly 化改造，以及把 Spec 写成「约束」（自动检查）与「假设」（允许 AI 按反馈调整）的分离。

2

平台能力亟须升级2.2

Agent 模拟人操作 Web UI 会遇到低效、知识散落、身份安全风险三重问题，而 CLI 因参数明确、输出可消费、退出码可判定，正成为 Agent 交互主流。三个递进问题：缺稳定可编程的系统入口（要统一入口而非更多 API）、缺完整确定的研发上下文（MCP 解决「如何调工具」，不解决「该操作哪个对象」，需要统一资源模型）、工具只给信息不推进任务（要返回「意味着什么」和「下一步做什么」）。解法是建设统一研发 CLI——给 Agent 一层可稳定进入、稳定理解、稳定推进任务的操作面。

3

提效度量2.3

只看「多少人用 AI、AI 写多少代码」必然跑偏——安装率含僵尸用户、Session 把闲聊当产能、AI 代码占比反向激励无效生成；度量对象必须从工具使用量转向研发生产系统的运行质量。方法是先打通 Session → Commit → Change → Workitem 归因主键链（「这条链路一旦断掉，指标就会失真」），再看三层证据链：L1 AI 效能、L2 工程质量、L3 价值交付；同时把 Skill / MCP / SPEC 等上下文资产纳入度量，并将度量前移到 Agent Loop，识别自主能力强弱。

4

数字员工2.4

当 Agent 成为独立行动主体，平台必须回答「哪个 Agent、在什么运行时、代表哪个用户、基于哪个任务、访问哪个资源、做什么动作、是否需要人批准」——这是从静态账号权限到运行时委托决策的变化。现有权限体系（人 / 应用 / 服务账号三类主体）装不下 Agent：复用人的账号审计分不清，复用服务账号责任找不到，当应用管则委托语义丢失。落地路线是「可见可管理 → 可控可复用 → 自主」三步走，组织虚拟员工与 Agent 原生身份授权两条路线并行；红线是数字员工不能成为绕过权限和责任体系的捷径。

5

组织配套2.5

康威定律、人月神话、Taylor 分工、manager 评价制等经典理论的隐含前提（沟通成本高、注意力稀缺、产出不可观测）正在失效，因为 AI 在这些维度上恰是人的镜像反面。组织设计正从 org chart 转向 execution graph，核心问题从 ownership（谁拥有）变为 routing（任务如何流转）+ governance（风险如何控制），「组织适应速度」本身成为最被低估的红利。但转型有真实代价——「蒸馏焦虑」（员工担心「把自己蒸馏完，就在组织里没位置了」，知识藏匿则 Harness 工作无法完成）与培养断裂（全行业不招 day 1，senior 池终将枯竭）；缓解靠明确 AI 红利分享方式、真实的「接住」机制、诚实分类岗位变化，以及让评价系统真正跟上——口头说「判断比执行值钱」但 KPI 还是产出量，员工不会信。

04

企业级 AI 研发基础设施全景

手册第三章

Harness 框架

以内部 Agent CLI 为代表的技术中枢，负责上下文管理、规划 / 状态 / 恢复、工具 / 验证 / 纠错、人机协同四项职责，把一次性生成变成「行动—验证—纠错」闭环。核心原则：安全与质量门禁必须由程序控制，不能只依赖提示词。第三章开篇的判断是——「软件交付的效率远远不等于 AI 生产代码的速度。」

企业知识库

不是 RAG 系统，而是一条「整理 → 加工 → 治理 → 供给」链路，把零散经验变成可访问、可验证、可治理的上下文。工具决定 Agent「能做什么」，知识库决定它「在什么条件下应当做、依据什么做、何时停止或升级给人」。

MCP / Skill / CLI 工具体系

MCP / CLI 解决「能做什么」（可调用的工具命令与可解析结果），Skill 解决「该怎么做」（任务方法、触发条件、步骤、约束）。以命中率 / 成功率双指标做工具评测，删除长期低命中、低成功的能力——从能力目录演进为可靠基础设施。

Sandbox 与 Coding 环境

Sandbox 是「可执行、可丢弃、受约束」的工作空间（容器只解决「在哪里运行」），四边界为生命周期控制面、实例内执行面、网络与访问边界（默认拒绝出站）、凭据边界（只给占位值、代理注入真凭据）。Coding 环境解决「仓库 ≠ 项目」——用可执行的项目运行上下文让「代码改对」变为「项目跑起来」，交付物从一份 diff 升级为一条可复现的验证路径。

身份与权限

把身份认证、委托、策略授权、凭证四个对象分开建模；经只读 → 受控修改 → 环境执行 → 高风险操作四阶段信任阶梯逐步放权，高风险默认不授予。

有效权限 = 用户权限 ∩ Agent 能力上限 ∩ 平台策略 ∩ 本次委托范围 ∩ 运行时约束

生产安全 Guardrail

Agent 进入高风险生产动作前的独立门禁（不是普通测试或审批）：核验证据完整性后放行，证据不足返回 UNKNOWN 而非默认通过；确定性规则引擎 + 独立评审模型双轨，Agent 不能自证通过。目标是把高风险动作转化为可核验、可解释、可恢复的流程。

可观测能力

分 System（系统运行是否正常：Metrics / Logs / Trace）与 Behavior（Agent 为何如此行动：核心原语 Trajectory，经统一 Trace Context 关联）两层；以级联漏斗（规则全量筛 → LLM 筛灰区 → 多维分析）控制语义分析成本。终点不是「看得见」而是「可改进」——观测数据同时是评测的核心数据资产。

给 Agent 平台负责人的 5 条启示

面向自研 TieAgent OS

1 · 把 Skill 从「能力目录」升级为「基础设施」，先建下线机制

Skill 规模一旦大起来，首要风险不是不够多，而是 Agent 选错。用手册 3.1.3 的命中率（是否选对能力）/ 成功率（是否用对参数、顺序、权限）双指标做全量评测，拆分臃肿能力、优化触发描述，并坚决删除长期低命中低成功的 Skill——工具治理必须包含下线。

2 · 安全设计的目标是扩大能力半径，而非收缩

智能体规模越铺越大，若长期只有粗放权限，永远不敢碰生产。按 3.3.1 把身份 / 委托 / 策略 / 凭证四对象分开建模，用「有效权限五项交集」替代查表式 RBAC，并引入 Challenge 三态（暂停 → 向人说明访问什么、为什么、影响什么 → 只签发覆盖本次调用的短期凭证），让高风险操作「默认不授权但可申请」。

3 · 主战场在验证与环境，不在模型

把「可复现的验证路径」定为交付标准而非 diff；环境定义即代码并版本化；对高价值场景引入「候选基线 + 销毁重建二次复验」机制；Sandbox 坚持默认拒绝出站、凭据只给占位值由可信代理注入——这些是智能体规模化后不翻车的底线。

4 · 度量前移到 Agent Loop，用证据链代替用量指标

Token / Session / 智能体数只适合冷启动。尽快打通 Session → Commit → Change → Workitem 归因主键链，建立 L1（AI 效能）/ L2（工程质量）/ L3（价值交付）三层互锁指标，并新增「人工干预次数 / 任务」度量自主性——万有无界「auto bug fix 60%+ 但日清率不动」的教训说明，缺了这项，瓶颈永远隐形。

5 · 先补协作协议与确定性约束，再追模型升级

自动化的瓶颈在「触发」和「校验」，不在「执行」：为智能体建「自己的钉钉」（任务路由、结构化交接契约、云上 Scrum 式随时协同）；所有必须严格执行的门禁走程序拦截而非写进 prompt；知识库按「整理 → 加工 → 治理 → 供给」链路建设，并把智能体使用反馈回流治理，让 Skill 背后的知识持续可信。
