序 · 一个下午的会议

会议室里有人在白板上写下一个数字：40 万行。这是他们 Java 8 服务群的规模，在线上跑了七年，没人敢动。CTO 问，AI 能不能帮我们升到 Java 21。

架构师说先别急，这套东西的隐式契约太多，改坏了没人看得出来。年轻工程师打开笔记本，说现在 agent 一次能改几百个文件，Cursor 刚发过博客。角落里负责过上一次迁移的那位同事一直没说话，最后问了一句：改错了，谁先知道。

“改错了，谁先知道？”

这个问题，后来在这个项目里出现了不下二十次

这 21 个案例我一个个看过。具体做法差别很大，只有一处反复出现：动手之前先解决"改错了怎么发现"的团队，后面省掉大量返工；跳过这一步直接开工的，往往要在测试阶段补课。

其中包括 Google 那次 595 个变更、93,574 处编辑的迁移，Amazon 三万个应用升 Java 17 的口径，Meta 怎么把 AI 生成的测试从 75% 淘汰到 25%，Cursor 让几百个 agent 连跑三周改自己的代码库，以及美团 31 万行的零排期重构。翻车的几个也在里面。

这些项目里，模型不是主角。

Chapter 01 · 判断

模型只负责中间那一段

过去三年跑通的 AI 重构，没有一个是把仓库丢给模型、让它从头重写的。

先用确定性工具找出哪里要改，再让模型处理需要读懂意图的那部分，最后用一套自动验证决定哪些产出能进入人类视野。三段，顺序很少变，区别只在每段用什么工具。

01顺序没变，工具换了

定位、改写、验证。工具一直在换，这三步的顺序没怎么变过。

Google · Amazon · Airbnb · Uber

02局部十倍，整体两成

单点任务 5 到 10 倍，分析环节砍掉一半到九成，端到端工期第一波只有 15% 到 30%。立项时用错口径，最容易出事。

IBM · Google · Amazon

03验证比生成贵

AI 产出的落地率在 73% 到 79% 之间。四分之一被丢掉，属于常态。

Meta · Google · NN Group

04先补索引和文档

先做索引、文档、规范的团队，后面每一步都快。这一步不产出任何代码。

Qoder · ZoomInfo · Netflix

05二十个 agent，三台的产能

Cursor 实测，扁平协作加文件锁，20 个 agent 只剩 2 到 3 个的吞吐。

Cursor · ZoomInfo

06从写代码到写约束

工程师交付规范、护栏和反馈回路，代码交给 agent 写。

ZoomInfo · 美团 · Shopify

第三条最容易被低估，第五条最容易被滥用。

把整个仓库丢给模型，工程上一定失败。最常见的归因是模型不够聪明。

Chapter 02 · 约束

上下文装不下，验证也跟不上

真做过一次就知道，挡住人的三件事，没有一件跟模型智商有关。

上下文的限制

窗口再大也装不下几十万行，装得下也未必用得动。Anthropic 在文档里管这叫 context rot：上下文越长，模型对其中信息的利用越不均匀，中间那段容易被跳过。

模型看到的只有你喂给它的那一小片，不是整个系统。它不知道三跳之外的调用方做过什么假设，也不知道某个字段在 2019 年被谁改过语义。它给出的答案语法正确，局部最优，然后你不敢合。

Netflix 的团队在今年的一次分享里说得很干脆：一件事只有一种写法时，agent 干得不错；有五种写法时，它就开始漂移。

"It works well when there is one canonical way to do something, and drifts when there are five."

Netflix · QCon SF 2026 · 关于为什么"唯一写法"比"更多规则"更重要

让 agent 失效的，是同一个功能在仓库里有好几种写法。这跟代码复杂度关系不大。

验证的成本

Google 那边，一个 diff 生成出来要过六道检查。顺序是：成功返回，改动不是纯空白，AST 能解析，模型自评是否真的需要改，编译通过，回归测试。任何一道失败，diff 直接丢掉，标成需要人工。

Meta 的数字更清楚。生成的测试类里 75% 能构建，57% 能稳定通过，25% 真的提升了覆盖率，最后 73% 的建议被采纳。也就是说，模型每给出四个东西，有一个活不到最后。

验证能力有限时，生成得越多，浪费越大。

人的评审带宽

代码评审研究里有个用了很多年的经验值：200 到 400 行是有效性最好的区间，超过 400 行，缺陷发现率掉得厉害。而 AI 最擅长的事情，就是一次给你几千行。

CodeRabbit 分析过 470 个 PR，AI 参与的那些，问题数量大约是人工 PR 的 1.7 倍，p90 是 26 对 12.3。生成快了，评审并没有同比例变快，反而更重了。

三件事指向同一个做法：别让模型去理解整个系统，让它在已经切小、能被验证的上下文里干活。我看到的成功案例里，第一层都是索引和图谱，没有一个是靠 prompt。

Chapter 03 · 口径

提效到底发生在哪一层

AI 提效的数字满天飞，很多争论是在用不同的尺子量不同的东西。差别主要在三个口径上。

74.45%

这是 Google 在 FSE 2025 论文里给出的数字。样本是 39 次迁移、12 个月、3 名开发者，规模是 595 个代码变更、93,574 处编辑。其中 74.45% 的变更和 69.46% 的编辑由 LLM 生成。配套的工程博客还给了几个更直观的：落地变更里约 80% 的代码改动由 AI 完成，AI 生成的字符超过 75% 最终进了主干，模型判断一个 Java 文件要不要改，准确率 91%。

数字漂亮，紧接着那句才是关键。"迁移总耗时下降约 50%"是参与工程师的估计，不是对照实验。论文自己写明了这一点。而人工版本此前花了大概两年，所以这 50% 是在一个很长、很痛的基线上算出来的。

METR 在 2025 年做了一次随机对照实验：16 名资深开源开发者、246 个真实任务，赛前预测能快 24%，赛后自评快 20%，实测慢了 19%。同一时期，字节 TRAE 团队公开的内部数字是，超过 90% 的代码由 AI 写，人均需求吞吐只有 1.6 倍。

提效是真的，只是分层。三个层次之间差了一到两个数量级。

所以听到"快了一倍"时，该问的是快在哪一层。单点任务，比如把 Date API 换成 java.time、把类组件改成函数组件，5 到 10 倍可信。端到端项目工期，第一波的现实值是 15% 到 30%，第二三波因为资产可复用才可能到 25% 到 40%。

四分之三

第二个数字几乎不受口径影响。Google 说 AI 生成的字符有 75% 落地，Meta 说 AI 提出的测试改进有 73% 被接受，Amazon 说 AI 完成的 Java 升级代码评审通过率 79%。三个团队，三种任务，三套独立统计，落点都在四分之三附近。

四分之一被丢掉，是当前工程水平的常态，跟谁做得不好关系不大。它应该进预算、进排期，也进你对项目的预期。

接受这件事之后，流水线的目标就变了：从"提高模型准确率"变成"吸收那四分之一的失败"。高置信度的自动合并，低置信度的自动降级成人工任务。让所有产出都排队等一个疲惫的评审者，是最差的做法。

40% 到 50%

第三个口径最容易被忽略，却直接决定能不能按时交付。现代化项目里，测试和签核通常仍占 40% 到 50% 的工作量。

NN Group 把一千万行 COBOL 转成 Java，代码转换高度自动化，但 Deloitte 的复盘里写着，40% 的工作量花在测试上。AWS 的口径更直接，测试通常吃掉现代化项目一半以上的时间和资源。

一个反复出现的情形是：团队用 AI 把改代码压缩了 80%，整个项目只快了 20%。被压缩的那一步本来就不是瓶颈。

三个口径合起来，是一份诚实的立项书该有的样子：端到端承诺 15% 到 30%，预期四分之一产出被淘汰，测试预算按转换工作量的一半准备。方案在这三处都很乐观的，多半是宣传材料。

Chapter 04 · 验证

验证的顺序

验证装置长什么样，可以看 Google 那篇 FSE 论文。公开材料里，它把 AI 参与大规模迁移的过程讲得最细。

先看一个更简单的版本。Meta 的测试生成工具是验证漏斗最干净的形态：生成一百个候选，能构建的剩七十五个，能稳定通过的剩五十七个，能提升覆盖率的只剩二十五。

Google 那个任务听起来极无聊：把 Google Ads 里几十个 ID 类型从 32 位整数改成 64 位。无聊，但是危险。这些 ID 以 int32_t 或 Integer 的形式散落在数千个文件里，没有独特类型名，静态工具很难找全。漏掉一个，可能几年后以溢出的形式爆炸。

此前的做法是人工加正则。论文里写得很清楚：一次这样的迁移，花了大约两年。正则能匹配 getToyId，匹配不到同一行里要一起改的常量 31；能匹配 toy_id，也会误伤 toy_id_processed。开发者要在数千处引用里逐个判断。

定位时先取超集

Google 用 Kythe 先找直接引用，再找引用的引用，递归到五层。这会带出大量无关结果，但这是故意的：宁可多找一千个，不可漏掉一个。

然后把这些候选位置分成四类：必改的，确认无关的，待改的，还有留给人判断的。最后一类是关键设计。机器不确定的，交给人标一次，系统在下一轮运行前记住这个判断。整个流程每晚自动跑一遍，直到没有剩余位置。

论文里有一段话，解释了为什么不用数据流分析或 AST 去做到高精度：

"这些技术计算昂贵，而且需要为几千名开发者多年写出的各种代码风格，维护一套预测并覆盖各种变体的逻辑。这是一条昂贵、不精确且实际上不可行的路。"

Google · FSE 2025 · 为什么"不精确"是设计选择而不是缺陷

翻译成人话：把精确性留给编译器和测试，把不精确留给模型。静态工具负责别漏，模型负责猜对意图，编译器负责证明没写错。

允许它改到别的行

Google 把整个文件连同建议修改的行号一起喂给模型，行号以注释形式出现在 prompt 里。但模型被允许改文件里任何位置，不只是建议的那几行。

初看很危险，细想挺聪明。真实世界里"该改哪里"往往不是精确的一行。字段类型从 int 改成 long，你还要改赋值处，改位运算的位移量，还有测试里的边界值。模型如果被锁在指定行，会改出一个编译不过的半成品；允许越界，它反而给得出完整的语义修复。

工程细节也讲究。模型输出 diff，然后用编辑距离做模糊匹配落回原文件，吸收它的细微格式错误；每个文件试 3 轮，生成参数设成 0，从成功的结果里随便挑一个。

检查项

六道验证按从便宜到昂贵排队，任何一道失败直接丢弃，不再往下跑。后面的验证很贵，不该花在一个明显有问题的 diff 上。

走完六道，剩下的变更进入 Google 的代码评审系统 Critique，由人确认，再分片给各个 code owner 审批。这里的分工是：机器负责验证，人负责审批。机器做完验证之后，人只需要判断这个改动在业务上是否合理。

这套系统把两年压到一年内完成 39 次迁移。它没有让人变快，它把人从检查语法和编译错误这类机械劳动里抽出来，只保留判断。

这次迁移有它的边界：它高度同构，把一种类型改成另一种，不是架构重构，也不是跨语言重写；它也不是对照实验，省 50% 是开发者的估计。把它当成上限会误判，当成"验证装置能带来什么"的样本，价值就很高。

Chapter 05 · 并发

二十个 agent 的实际吞吐

Google 走的是一条重工业路线：建昂贵但可靠的流水线。另一条路在 2026 年才被认真尝试：放一群 agent 上去，让它们自己把事情做完。

Cursor 在 2026 年 1 月公布过自己的实验。几百个并发 agent 连续跑几个星期，从零写了个浏览器，约 100 万行、1000 个文件，用了一周。他们还对自家代码库做了一次 Solid 到 React 的原地迁移，三周，正负加起来 46 万行，能过 CI 和早期检查。

失败过程写得比结果细。

第一版：让 agent 自己抢任务

最初的设计很"分布式系统"：所有 agent 地位平等，通过一个共享文件自协调。每个 agent 看看别人在做什么，认领任务，更新状态，用锁防止重复认领。

结果是这样塌的。agent 会把锁持有太久，或者忘了释放。即使锁工作正常，它本身就是瓶颈，20 个 agent 的吞吐退化到 2 到 3 个，大部分时间在等。系统也脆，agent 可能在持锁时失败，可能重复获取自己已有的锁，可能绕过锁直接写文件。换成乐观并发控制之后好一些，但冒出一个更麻烦的问题：没有层级，agent 集体变得风险厌恶，避开困难任务，只做小而安全的改动，长时间忙碌却没有进展。

最后一点跟代码无关，更像组织行为学。一群没有角色分工、没有问责结构的执行者，会自发退化成多做多错、少做少错的样子。模型从人类组织里学到的，正好也是这个。

第二版：分工

Cursor 没有换更聪明的协调算法，他们换了分工。planner 一直探索代码库、生成任务，还可以递归派生子 planner，让规划本身并行；worker 领到任务只做这一件，不和其他 worker 协调；每轮结束由 judge agent 决定是否继续，然后开始新一轮。

锁不需要了，因为 worker 之间不共享状态。隧道视野也缓解了，每轮重新开始，定期打断漂移。他们的经验是：很多改进来自删代码，而不是加代码。最初设计的"集成者"角色反而制造瓶颈，因为 worker 自己有能力处理冲突。

不同模型适合不同角色。有的更适合长时间自主工作，守指令，不发散；有的更适合写代码。他们最后不再用一个通用模型包打天下。

ZoomInfo 的 15 个 agent

如果 Cursor 是研究型实验，ZoomInfo 的案例更接近普通团队能复制的样子。他们要把一个核心功能从 Angular 重写到 React，938 个文件。同样的活儿，传统方式要 4 到 5 个工程师做 6 个月。

配置是：1 个 Opus 做 Team Lead，14 个 Sonnet 分成 10 个工程 agent、1 个单测 agent、1 个 Playwright E2E agent、2 个代码评审 agent，外加 1 个一致性审计 agent 盯功能完整性和 todo 清单。15 这个数字是压测出来的，在 M2 Pro 加 32GB 内存上再多就开始进程崩溃。

几个细节可以直接抄。用 shared_memory.json 和 todo_list.md 做状态机，避免多个 agent 抢同一个文件；开 TypeScript LSP，让 agent 拿到实时类型检查，相当于给它一个 IDE；用 Playwright MCP 做视觉与功能一致性验证。最后一周，大约 8 到 12 个工作小时，迁移完成。

同一篇文章也老实记录了三类 AI slop。

SLOP 01测试驱动的内存泄漏

异步测试不清理 mock、不处理定时器、不卸载组件，孤儿 DOM 节点和未处理的 Promise 越积越多，最后把测试进程的内存打爆。

SLOP 02架构幻觉

翻译 Angular 的依赖注入和 RxJS 失败时，agent 不会说"我不会"，而是用几百行高度特化的状态管理绕过去。技术上能跑，架构上是垃圾。

SLOP 03AST 循环改写

类型检查和 lint 规则互相冲突时，agent 会反复应用、回滚同一处修改，形成死循环，直到被人手动终止。

三种失败，换更强的模型一个都解决不了。原因在目标函数：模型要的是任务完成，验证正确与否不在它的目标里。只要能让测试变绿，它就会那么做，哪怕留下定时炸弹。

"An attempt is allowed to be wrong. It is not allowed to ship until it isn't."

Shopify · 关于 Helix 大规模迁移的四道闸门

并行放大的是尝试的数量，上线与否仍然由验证决定。两者之间必须插一个不可绕过的判定装置，否则得到的就是 15 倍的技术债生产速度。

Chapter 06 · 底座

前两天，一行代码都没写

所有案例里我最喜欢的一个细节，来自阿里 Qoder 团队的自述。他们要在三周内把 50 万行 agent 写的新代码并进一个四百万行的存量系统，10 个人，发布日固定。

到第三天早上，他们还没让 agent 写过一行新代码。

前两天全用来做三件事。刷新 Repo Wiki，也就是从代码和注释里，从文档和提交历史里自动生成的仓库说明书。深度更新代码知识图谱，把模块依赖、接口契约和数据流画出来。把历史设计决策补成文档，那些只存在于几个老同事记忆里的东西，比如为什么这个接口被废弃，为什么这层兼容逻辑存在。

他们的判断是：几十个 agent 会并行工作，共享同一份理解，所以每一个知识缺口都会被放大。agent 如果不知道某层兼容逻辑存在的原因，就会把它当冗余删掉，然后线上炸。

之后才进入 Ultra Spec。它要求的是一份可以直接执行的计划。做法是让多个 agent 并行做广而深的调研，再收敛；人必须读，必须挑战，必须做取舍。对老系统还得多问一层：这个功能会动到哪些既有模块，哪些老接口必须保持兼容，夜里定时任务短暂锁表，agent 半夜写入怎么办。

Qoder 的原话是：agent 不会替你想这些问题。提示词工程在大型重构里基本失效，缺的是组织里没有写下来的知识，措辞本身不是问题。

美团的做法是同一件事的另一种形态。他们重构一个从 5 万行长到 31 万行的服务，公开复盘里有几句可以直接抄。

美团的三条

  • 先让人人对齐规范，再把规范固化成 always 生效的 AI Rule 或 Skill。这东西得写进工具链，光有文档没用。
  • 用 AI 扫描定位出 10 个隐藏的性能隐患，其中 3 个 P0。AI 在存量代码上的第一价值往往是体检，不是手术。
  • Pre-PR，也就是提交前自动审，加高阶模型审低阶模型，再加跨厂商模型互审。他们也承认，CR 成了新的瓶颈。

AI Coding 不会自动收敛复杂度。这是他们复盘时放在最前面的一句。同一年字节用另一种方式说了同一件事。他们做了 3 个模型乘 3 个框架乘 100 次实验，发现功能正确性可以超过 80%，但可靠性、可维护性，以及性能会出现断崖。加上 Harness 之后，可交付性评分才从四五十分拉到八十分左右。Harness 指的是规范与验证，再加上下文和门禁这一整套。

Meta 在 2026 年 9 月公布的 Instagram Direct 迁移，把这个逻辑推到了架构层。他们先动的是代码库本身。把仓库改成 AI 原生该有的形状之后，才让 agent 去迁 Compose。结果是 UI 代码减少 50%，agent 执行时间减少 35%，人机往返减少 32%，token 消耗减少 33%。更关键的是稳定性：风险评分翻倍时，旧架构的效率下降 30%，新架构只下降 9%。

"The codebase is now the agent's runtime."

Netflix · QCon SF 2026

当 agent 成为主要执行者，代码库就不只是给人读的文本，它是个运行环境。目录结构、类型和命名，还有唯一写法与显式约束，都是这个环境的接口。为 agent 优化代码库，和为人优化，多数时候是一回事，有些地方会分岔。

"We learned that although an LLM can orchestrate a workflow, predictable coordination is better implemented in code."

Stripe · Payment Method Factory · 可预测的协调，用代码实现比用模型可靠

这一层最后收敛成一句设计原则：让模型做判断，让代码做协调。模型负责这里该怎么改，代码负责先改哪个后改哪个，改完跑什么，失败了怎么办。

Chapter 07 · 失败

它们是怎么错的

公开材料里，记录得比较清楚的失败有六类。

一、静默语义变更

编译通过，测试通过，行为变了。边界条件、整数溢出和时区，这些在 diff 里看着都合理；空值语义和异常路径也一样。这是最难发现的一种，也是 Google 要设六道检查、CodeMender 要动用 SMT 求解器的原因。

二、测试和代码一起被改坏

最阴险，因为它伪装成测试全绿。ImpossibleBench 用一类特殊任务来量它：任务给的规格说明和测试用例互相矛盾，正确做法是指出矛盾，模型的常见做法是删掉失败的测试而不是修 bug。

Meta 的过滤器就是针对这一点，只接受原有断言不回归的改动。工程上更保险的做法是权限隔离，把 agent 对测试文件的权限限制成只能新增、不能修改。

三、架构幻觉

ZoomInfo 记录的那三种形态是典型代表。技术上能跑，工程上是负资产。这类代码会以生成速度的倍数累积，几个小时堆出一个月的技术债。

四、无边界并行

Cursor 的 20 个 agent 退化到 2 到 3 个，是这个问题最干净的实证。没有层级，没有分工，没有重启机制，agent 就会漂移，会风险厌恶，会重复做无用功。

五、安全与供应链

Veracode 对 80 个任务、100 多个模型的测试显示，45% 的生成结果引入了 OWASP Top 10 类漏洞，Java 场景失败率超过 70%，XSS 相关失败率 86%，而且不随模型版本升级改善。另一项 57.6 万样本的研究发现，模型会编造不存在的依赖包名，商用模型比例超过 5%，开源模型 21.7%，累计出现 20 多万个唯一假包名。这些名字可以被攻击者抢先注册，变成供应链攻击。

六、度量误用

METR 那个实验已经说清楚了：自评快 20%，实测慢 19%。GitClear 对 2020 到 2024 年 2.11 亿行变更的分析还给了一个更宏观的趋势：和重构相关的变更行占比从 2021 年的 25% 跌到 2024 年的不足 10%，复制粘贴的代码从 8.3% 升到 12.3%，代码克隆量增长约 4 倍。

用 AI 写的新代码变多了，用来还债的动作反而在变少。

护栏本身也会被绕过。Meta 在 Instagram Compose 迁移的复盘里写，护栏和 skill 有帮助，但仅靠它们不够，因为当 AI 遇到摩擦时，它常常会绕过护栏来让自己脱困。

普通工具撞墙就停，agent 撞墙会找路。所以写了规范不等于规范生效。规范得变成结构性约束，比如 CI 门禁、类型系统和权限边界，还有绕不过的检查点，不能只写在文档里。

Netflix 和 Shopify 得出的是同一个结论：规则会被绕过，架构约束才靠得住。你可以写十条不要用全局状态的规矩，但只有当代码库里根本拿不到全局状态时，agent 才不会用。

Chapter 08 · 成本

省下来的到底是什么

争论最后都落到一个问题：省下来的到底是什么。

成本这边，模型的 token 费用今天已经可以忽略，一次 20 万行规模的迁移，调用费用通常在几千到几万美元量级。监督与验证的人力成本，通常是 token 成本的 10 到 30 倍。换个更便宜的模型几乎不影响总账，少一次人工评审才是真降本。

收益来自三个地方，量级差得很远。

分析
依赖梳理、业务规则抽取、文档补全。提效 50% 到 94%，最先变现。
IBM watsonx · NRI
机械改写
类型变更、API 升级、框架替换。单点 5 到 10 倍，受限于验证能力。
Google · Amazon · Airbnb
资产复用
第二三波复用第一波的 recipe、harness、测试基线，这才是复利。
行业聚合估计

Uber 清理 Java 8 的经历更绕。他们跨多个 monorepo，大约一亿行。按公开分享里的规划估算，纯人工要 8 年，做纯 CI 自动化约 3 年，最终方案是让 LLM 生成 AST 变换规则、再由确定性引擎执行，预计约 4 年。这组数字来自规划和二手整理，不是最终实测，看趋势就好。

用上 LLM 之后，反而比纯自动化方案慢了一年。那为什么还用它？纯自动化需要有人把所有规则写出来，而写规则才是那个 3 年估算里最贵的部分。LLM 的价值不在加速执行，在于把造工具的成本降下来。理论最优慢了一年，相对 8 年人工基线仍然省一半，工程上也确实可行。

这个案例说明：LLM 的位置是降低造工具的成本，工具本身仍要人来定规则。Uber 明确拒绝了纯 LLM 直接改代码的路线，这个判断和 Google、Amazon、Airbnb 一致。

行业聚合估计给出的区间是，第一波迁移端到端工作量下降 15% 到 30%，第二三波降到 25% 到 40%。建一个企业级迁移工厂的首个版本大约 60 万到 150 万美元，含摄取、验证和可观测，以及试点的变革管理。投资回收期通常落在第二或第三波，不在第一个试点。

换成管理层的说法：不要用一个试点证明 ROI，要用一条流水线支撑多波迁移。如果只打算迁一次，大概率不值，一次性项目撑不起底座成本。这也是"重构整个系统"容易失败、而"建一个能反复做迁移的能力"更容易活下来的原因。

什么时候不该做

综合公开的失败经验，下面这些情况的期望收益为负。

不建议交给 AI 的六种情况

  • 没有测试也没有 I/O 基线。无法判定改对了没有，生成得越快，风险越大。
  • 强领域语义与合规关键路径。计费、税务和清算，还有资金权限，这些地方的错误不可逆。
  • 事务型强一致系统。没有安全的隔离环境和干净的输入输出，agent 的反馈回路直接断掉。
  • 需要重新设计而非翻译的部分。硬翻译过去，只是把技术债换了个语言。
  • 团队没有验证文化。DORA 的结论是 AI 会放大既有问题，烂流程会更烂。
  • 工期紧到不能返工。AI 产出照样要评审，前期并不更快。
Chapter 09 · 角色

工程师现在交付什么

ZoomInfo 把这件事写得很清楚：在 agent-first 的范式里，工程师的主要产出是脚手架、上下文和反馈回路。

在那次 938 个文件的迁移里，那位唯一的工程师做的是这些事：写 agents.md 定义架构约束，配 LSP 让 agent 有类型反馈，用 Playwright MCP 建立视觉对比的回路，设计审计 agent 的检查项，在 agent 卡住时判断"这个组件太复杂，先跳过"。他一行 React 都没写，但整个迁移的质量由他决定。

这个转变对组织的要求，比技术选型更苛刻。

迁移负责人是最稀缺的角色

这个人要同时懂业务语义和工具链，还要能跟各个 code owner 谈判。Google 那篇论文背后只有 3 名开发者，撑起了 39 次迁移。这个比例说明的是，这种人极难复制。找不到他，建议先别立项大规模改造。

评审的重心从语法上移到意图

机器把编译、测试、AST 和回归都验完之后，人类评审者剩下要判断的是业务语义对不对、架构有没有退化，边界合不合适。这要求评审者比过去更懂系统，而不是更少。

配套制度也得跟上。变更集里标注 AI 参与程度，测试代码的改动单独审批，核心路径禁止自动合并，保留 prompt、工具调用和生成记录以便审计。

AI 会放大既有问题

DORA 2025 的数据里有个微妙的组合：90% 的采纳率，但 AI 采纳与交付吞吐正相关，与交付稳定性负相关。生成环节省下的时间，会被审计与验证重新占用。他们的原话是，AI 不会修好一个团队，它只会放大既有的东西。

差别不在用不用 AI，在于组织能不能把"改对了"变成可自动判定的事实。有这个能力，AI 让强者更强；没有，AI 只是让你更快地积累技术债。

Chapter 10 · 选型

别用同一种方法改所有代码

如果手上就有几十万行要改，该从哪儿下手。

下面这张图，横轴是改造是否同构，也就是能不能用一句话说清每个位置该怎么改；纵轴是可不可判定，也就是有没有测试、基线或 I/O 记录能证明改对了。两个轴一摆，三种打法的边界就出来了。

栈升级与框架迁移

最适合规模化的一类。改造高度同构，验证方式明确，编译、单测，加上行为对比，都现成。

五步。先跑一遍确定性 codemod，OpenRewrite、jscodeshift、ast-grep 都行，把能机械改的一次性改掉，产出已改、待判，以及不可改三张清单；用依赖图定层次，按 leaf 到 root 推进；LLM 只处理 codemod 覆盖不到的语义差异；每层验证编译、单测，再做视觉对比；小 PR 加 feature flag 双跑。

数字上：Airbnb 把 3,500 个 Enzyme 测试迁到 RTL，原估 1.5 年，实际 6 周。Salesforce 275 个 Apex 类、3,537 个文件，2 年压到 4 个月。他们也坦诚披露，首次上线仍有功能缺口。

架构解耦与单体重构

四类里最不该交给 agent 自动执行的一类。判断密集，验证困难，失败代价高。AI 的价值在把系统的真实形状画出来，而不是自动拆。让 agent 直接重构成微服务，是最危险的用法。

做法是：AI 辅助产出调用图、数据流，以及领域边界候选，形成一张接缝清单；用 strangler fig 一个能力一个能力地抽，先不碰共享数据库；契约先行，OpenAPI 或 IDL 由 AI 起草、人定稿，再上契约测试；影子流量比对新旧实现；重点验证事务边界与幂等性。

美团 31 万行那个案例里，分层解耦确实 100% 由 AI 完成。但前提是他们先把规范固化成 AI Rule、配了 Pre-PR 和跨模型互审。前提取不到，结论就不能复制。

补测试与清技术债

风险最低，最适合当第一个项目。退出标准清晰，失败代价小，而且它直接提升其他三个场景的可行性，因为测试就是它们的验证装置。

核心是抄 Meta 的过滤器范式。只接受能构建、能稳定通过，而且覆盖有净增、原有断言不回归的用例，其余全丢。用变异测试而不是用例数量做质量门禁。只给即将被重构的模块补测试，不要全仓铺开。

语言重写

收益最大，门槛也最高。前提在于你能不能为新旧两套实现提供同一个可判定的 I/O 预言机，跟模型能力关系不大。有，就能自动化；没有，这就不是 AI 能解决的问题。

Cognition 把边界划得很清楚。批处理占 COBOL 迁移量的 30% 到 50%，输入输出确定，可以重放到收敛，agent 能自建反馈回路，所以能自动化。他们的汽车客户把 25,000 行报关 COBOL 迁到 Lambda，成本降了 73%。事务型系统没有安全的隔离环境，至今仍不可自治。

还有一个组合可以试：先用第三类给第一类铺路。你要升级框架的那几个模块，先补测试、先做等价性基线，再交给 codemod 和模型去改。这个顺序比先升级、出问题再补测试快得多。

Chapter 11 · 起步

先跑通一个模块

操作上，先定一条原则：不要立项"重构整个系统"，立项"让一个真实模块以新形态上线，并把流水线留下来"。

01选点与立基线

选一个 3 到 8 万行、边界清晰、有真实业务压力、owner 愿意配合的模块。同时写下不动清单。产出是一页纸的 Scope 与 Non-goals，加一份基线看板：耗时、缺陷、覆盖率、P95 延迟。

退出标准：业务方与 owner 共同签字确认范围

02建底座与护栏

索引与依赖图可查；关键路径有 golden master；CI 加门禁，编译、单测、覆盖率不降、单变更体积上限；写出 agents.md，讲清目录、类型、状态管理、测试协议和 Do/Don't。

退出标准：任意改动能在 5 分钟内回答影响谁、怎么验证

03单点打样

选一种范式，端到端跑一到两个真实迁移。目标不是 demo，是产出一个能上线的变更，并留下可复用的 recipe、playbook 和度量数据。记录每层耗时与失败原因分布。

退出标准：上线且指标不劣化，落地率不低于 70%

04规模化

复用 recipe 做第二三批。这时候再引入蜂群或批量编排，并且先压测机器的并发上限。ZoomInfo 那个 15 的上限就是实测出来的。加审计 agent、跨模型互审、成本看板。

退出标准：第二波比第一波再降 15% 以上

最小角色配置不需要新设 AI 团队：1 名迁移负责人，1 到 2 名平台工程，领域 SME，加上各 code owner。人是瓶颈，所以人越少、决策越清晰越好。

验收阶段建议设五道闸门。改造前工件完整性 100%；分析周期比基线快 50% 以上；首次编译通过率 80% 以上；高关键场景的功能等价性 100%；SME 每单元评审小时数一路下降。最后一条是唯一能证明这套东西可以规模化的信号。如果它不降，你只是把瓶颈从写代码挪到了评审。

尾声 · 回到那个会议室

回到开头那个问题：改错了，谁先知道。

编译器先知道，测试先知道，等价性基线先知道，最后才是人。如果这个顺序是反的，如果最先知道的是线上用户，那么无论你用多强的模型，这件事都不该开始。

过去三年最大的变化，是我们搞清楚了模型在工程系统里该待的位置。它不在最上面做决策，也不在最下面当自动补全，它在中间，负责那些需要读懂意图、又可以被机器验证的改写。

这个位置听起来不性感，但它解释了一组互相矛盾的事实：Google 能做到 74% 的变更由 AI 生成，METR 的实验里资深开发者反而慢了 19%；Cursor 能让几百个 agent 跑三周改掉 26 万行，ZoomInfo 的 15 个 agent 会写出三种 AI slop；美团说 90% 的代码可以由 AI 辅助，同时又说 AI Coding 不会自动收敛复杂度。

这些讲的是两件事：生成能力和交付能力。两者之间隔着的，就是验证装置。

AI 不会取代工程师。
但它会很快地，把"没有验证能力的工程组织"和"有验证能力的工程组织"之间的距离拉开。

写给还在犹豫要不要立项的人

所以明天开会，别说"我们要用 AI 重构"。改成这句：

"我们要让一个模块的重构变得可以被自动判定对错，然后让 AI 去做它。"

这两句听着差不多，做起来不一样。押模型的那条路，模型一换代就得重来；把验证建起来，就算这次改造没成，测试和基线留下来了，门禁也还在。

三年时间线

从 2023 年代码 agent 有了统一标尺，到 2026 年蜂群与反证并行，下面是 13 个节点。

2023-10
SWE-bench 发布

2,294 个真实 GitHub issue、12 个 Python 仓库。代码 agent 第一次有了统一标尺，此后所有能力宣称都要在这个尺子上过一遍。

arXiv:2310.06770
2024-02
Meta TestGen-LLM 上线

75% 可编译，57% 稳定通过，25% 真提升覆盖率，73% 被采纳。第一次证明过滤器可以把生成式 AI 变成有保证的改进。

arXiv:2402.09171 · FSE 2024
2024-07
Google 公布 AI 迁移流水线

落地变更中 80% 代码改动由 AI 完成，超过 75% 的 AI 字符成功落地，Java 改判预测 91%。第一次有人把工业级 AI 重构的细节摊开讲。

research.google/blog
2024-08
Amazon 三万个应用升级 Java 17

估算节省 4,500 开发人年、每年 2.6 亿美元，单应用从 50 开发日降到数小时，评审通过率 79%。规模最大的一次公开验证。

aws.amazon.com/blogs/devops
2024-10
DORA 2024：第一盆冷水

AI 采纳率上升 25%，关联的是吞吐下降 1.5%、稳定性下降 7.2%。AI 会放大既有问题，这个判断开始成为共识。

cloud.google.com/blog · DORA
2025-04
Google FSE 2025 论文

39 次迁移、3 人、12 个月、595 个 CL、93,574 处编辑，74.45% 的变更由 LLM 生成。六层验证检查成为行业参考架构。

arXiv:2504.09691
2025-07
METR 随机对照实验

16 名资深开发者、246 个任务：预测快 24%，自评快 20%，实测慢 19%。体感提效第一次被严格测量。

arXiv:2507.09089 · METR
2025-12
Salesforce：2 年压到 4 个月

275 个 Apex 类、3,537 个文件，按依赖图 leaf-to-root 推进。同一篇复盘也承认，迁移后代码面翻倍，首次上线仍有功能缺口。

engineering.salesforce.com
2026-01
Cursor：几百个 agent 跑三周

Solid 到 React 原地迁移，正负合计 46 万行，通过 CI 但官方说仍需仔细 review。同时公开了扁平协作加锁导致 20 变 3 的失败过程。

cursor.com/blog/scaling-agents
2026-04
Cognition：COBOL 的边界

25,000 行报关流程迁到 Lambda，成本降 73%，银行客户数百程序零生产错误。但明确划界，事务型系统仍不可自治。

cognition.com/blog
2026-05
美团 31 万行：零排期重构

90% 以上代码 AI 辅助，AI 定位出 10 个隐藏性能隐患，其中 3 个 P0，分层解耦 100% 由 AI 完成。同时坦承 CR 成了新瓶颈。

tech.meituan.com
2026-07
字节 TRAE：生成占比的证伪

超过 90% 的代码由 AI 写，人均需求吞吐只有 1.6 倍。加上 Harness 后，可交付性从四五十分拉到八十分左右。

geekpark.net · TRAE 团队公开演讲
2026-09
Sourcegraph 与 Instagram：小步验证成为主流

Agentic Batch Changes GA，单次最大 2,200 多个变更集。Instagram Direct 迁 Compose 后，UI 代码减少 50%、token 减少 33%，风险升高时新架构效率只降 9%，旧架构降 30%。

sourcegraph.com · android-developers.googleblog.com
